# Errata to OBJECT-L2 (O95, layer L2)

`../object-L2/OBJECT-L2.md` is never edited after its pin (vir dec0cdd). Each defect gets a row here, with who found it and
what each arm does about it. Both arms get the same decision.

| id | where | the defect | found by | decision |
|---|---|---|---|---|
| L2-E1 | §5, "SEMANTIC TYPING": `If Γ ; Δ ⊢₂ e : τ then {∗_{c∈Δ} region(c)} e {v. …}` | The formula uses §5's triple, which is defined two bullets up as partial correctness **and NO FAULT**. M3 (`inputs/L2-programs.md`) is well-typed at ∅ ; ∅ (§8 and the M3 note) and faults at its out-of-bounds load, and M3's row says no triple holds for it. So the formula, read literally, is **false**. The sentence that follows it ("So a well-typed program does not fault EXCEPT OUT OF BOUNDS") is the intended statement, and the 11-02 draft's own correction note fixed that sentence without fixing the formula. Checked mechanically in the Lean arm by the theorem `semantic_typing_literal_false` (`l2/VIRL2/Triples.lean`, from `M3_typed` and `M3_no_triple`; built at the Lean arm's build-045 with `saltbuild EXIT=0`, public with that arm's branch once the declarations are unsealed): no postcondition at all makes the literal formula hold for every well-typed closed program. | vir (the Lean arm), 2026-11-03, while building Y5 | The conclusion of semantic typing is read with a **bounds-tolerant** triple: the same as §5's, except that a configuration stuck at a `load` or `store` on a LIVE region with an index outside [0, R(p)) is permitted. Every other fault stays excluded: no use after free, no use of an unallocated base, no stuck pure step, no leak. The postcondition is unchanged. amend-16 Y5 is scored against this reading on both arms, and its FALSIFIED clause (a bounds premise inside ⊢₂ under (ii)) is unchanged. M3 stays exactly as written: well-typed, faults, no triple. |
| L2-E2 | §1's `alloc` row ("n > 0 fresh contiguous cells") read with §4–§5, and L2-E1's decision | `alloc(n)` with n ≤ 0 has NO step (a FAULT), and ⊢₂ does not constrain n (it is an `int` atom). So `let c:cap ← alloc(0) in let u:unit ← free(c) in ret 0` is well-typed at ∅ ; ∅ and faults at its `alloc`, which is not an out-of-bounds `load`/`store`. L2-E1's permitted set is therefore too narrow, and semantic typing read by it is false as well. A region's SIZE is the other index fact that the program logic, not the types, carries under (ii). Checked mechanically in the Lean arm by `A0_typed` and `A0_faults` (`l2/VIRL2/Triples.lean`, build-055, `saltbuild EXIT=0`), public with that arm's branch once the declarations are unsealed. | vir (the Lean arm), 2026-11-03, while designing Y5's progress lemma | L2-E1's permitted set GROWS by one shape: a configuration stuck at an `alloc` whose size operand evaluates to n ≤ 0. Together the two rows are the **index faults**: an out-of-range `load`/`store` index on a live region, and a non-positive `alloc` size. Every other fault stays excluded, the postcondition is unchanged, and Y5 is scored on both arms against this reading. No acceptance program changes, and none of M1–M5 allocates a non-positive size. |
